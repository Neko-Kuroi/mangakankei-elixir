# yomima_ex 解説ガイド

マンガ閲覧側「よみま」を Elixir で書き直した実装（`yomima_ex`）の解説です。
Elixir に詳しくない人向けに、構成・仕組み・運用方法をまとめました。
開発の経緯と検証の記録は `SPIKE.md` にあります。

---

## 1. これは何か

- アップロード側の「プラットフォーム」（Python / FastAPI）は**無改造**です。
  本プロジェクトは、その相方である**閲覧側だけ**を Elixir で実装し直したものです。
- Python 版の閲覧側と**差し替え可能**です。同じプラットフォームに対して、
  どちらを繋いでも同じ振る舞いをします（検証で1件ずつ突き合わせて確認済み）。
- 位置づけは「なぞり実装」です。新機能は足さず、Python 版の契約
  （URL、応答、文言、エラーコード）をそのまま再現することを目的にしました。

全体のつながりは次のとおりです。

```
読者のブラウザ
    │  画面表示・画像の復号はブラウザ側
    ▼
閲覧側 yomima_ex（この実装、:8001）
    │  カタログ取得・ログイン代理・CBZ の取得（内部トークンで連携）
    ▼
プラットフォーム（Python、:8000、無改造）
    │  作品データ（CBZ）の置き場所は外部ストレージ
    ▼
外部のファイル置き場
```

閲覧側の仕事は大きく3つです。

1. プラットフォームからカタログと作品（CBZ）を取り寄せ、読者に見せる
2. 読者のログインをプラットフォームへ代理し、許可制・年齢確認の門番をする
3. ダウンロードした CBZ を手元にキャッシュし、展開してページ画像を配る

## 2. Elixir 側の構成と考え方

大きな枠組み（Phoenix）は使わず、最小の部品で組んでいます。

| 部品 | 役割 | Python 版での対応 |
|---|---|---|
| Bandit | Web サーバー本体（リクエストを受ける） | uvicorn |
| Plug | URL の振り分けと共通処理 | FastAPI のルーティング |
| Req | プラットフォームや外部への HTTP 通信 | httpx / requests |
| Jason | JSON の読み書き | 標準の json |
| :image | 画像のリサイズ・変換（libvips の Elixir 側） | Pillow |

状態（セッションなど）の持ち方が、Elixir らしい部分です。Python 版では
プログラム内の辞書に入っていたものを、Elixir 版では **Store という
「状態専門の番人プロセス」** が一括で持っています。Erlang/Elixir では、
小さなプロセスがそれぞれ独立して動き、状態を持つ担当を決めておくのが
流儀です。番人プロセスは Supervisor（監督役）の下にあり、万一落ちても
自動で立て直されます（ただし状態はメモリ上だけなので、落ちれば
ログインやセッションは消え、読者は再ログインになります。これは
Python 版でも再起動で消える点は同じです）。

### ファイル構成（lib/）

| ファイル | 中身 |
|---|---|
| `router.ex`（946行） | URL の振り分けと各エンドポイント本体。Python 版 `yomima/main.py` の受け口に相当 |
| `manga.ex`（740行） | CBZ のダウンロード・展開、宛先ポリシー、サムネイル生成、Discord 送信、共有リストの変換。Python 版 `yomima/manga.py` に相当 |
| `reader_page.ex`（667行） | リーダー画面（HTML と復号スクリプト） |
| `list_page.ex`（239行） | ホーム画面（マイリスト）と、追加・削除で返す部分 HTML |
| `platform.ex`（168行） | プラットフォームとの通信。カタログの60秒キャッシュ（CatalogCache）も同居 |
| `store.ex`（180行） | 番人プロセス。セッション・ログイン・年齢ゲート通過・許可済み作品・展開結果・クライアントキーの秘密を持つ |
| `client_key.ex`（113行） | レート制限のクライアントキー（後述） |
| `application.ex`（19行） | 起動係。Store、カタログキャッシュ、Web サーバーを順に立ち上げる |
| `yomima_ex.ex`（18行） | アプリの看板だけの小さなファイル |

プロジェクト定義は `mix.exs`、依存のバージョン固定は `mix.lock` です。

## 3. 主な処理の流れ

### 3.1 カタログと公開画面

プラットフォームの公開カタログを取り寄せて一覧表示します。取得結果は
60秒間キャッシュし、プラットフォームへの問い合わせ回数を抑えます
（これは Python 版と同じ仕様で、管理者が作品を停止した場合に一覧から
消えるまで最大1分かかる、という性質も同じです）。

### 3.2 読者ログインとクライアントキー

読者のログイン・登録は、閲覧側がプラットフォームへ代理送信します。
このとき2つの目印を付けます。

- **内部トークン**（`MANGA_INTERNAL_TOKEN`）：「閲覧側からの通信です」
  という合言葉。プラットフォームと閲覧側の両方に同じ値を設定します。
- **クライアントキー**：プラットフォームの認証レート制限（ログイン
  5回/分、新規登録 3回/時）は本来 IP 単位ですが、閲覧側経由では全読者が
  閲覧側サーバーの IP を共有してしまい、他人同士で枠を取り合います。
  そこで閲覧側が、読者の実 IP から **HMAC-SHA256（秘密, 読者IP）** という
  64文字のキーを計算して一緒に送り、プラットフォームが読者ごとに
  枠を数えられるようにしています。生の IP は送りません（単純なハッシュ
  だと IPv4 は総当たりで元に戻せるため、鍵つきの HMAC にしています）。

秘密は閲覧側だけが持ち、解決順は次のとおりです。

1. 環境変数 `MANGA_CLIENT_KEY_SECRET`
2. 起動フォルダの `instance/client_key_secret` ファイル
3. どちらも無ければ初回に生成して同ファイルへ保存（権限 0600）

秘密が変わるとキーも変わり、レート制限の枠は数え直しになります
（いたずら目的では変えようがないので、運用上は問題になりません）。

### 3.3 リーダーを開く

1. ブラウザが作品の URL を渡してセッション発行を依頼する
2. 閲覧側は作品の種類を確認する
   - 許可制（premium）の作品：ログイン中であり、かつその読者に許可が
     出ている場合だけセッションを出す（許可の確認は閲覧側が保持し、
     CBZ 取得時には読者のトークンをプラットフォームへ併送して
     プラットフォーム側でも検証する二重構え）
   - 年齢対象の作品：ログイン中ならアカウントの年齢申告、匿名なら
     セッション単位の自己申告ゲートを通った場合だけ出す
3. セッションが取れたら CBZ をダウンロードし（進捗は SSE で通知）、
   初回表示時に展開する。展開したファイル名は Python 版と同
